# Spring 循环依赖与三级缓存（面试重点）

> 对应讲义 9.1 ~ 9.5 节。循环依赖 + 三级缓存是 Spring 面试**最高频的 TOP 级问题之一**，实习面试几乎必问。

---

## 一、什么是循环依赖

两个（或多个）Bean 互相持有对方的引用，形成依赖闭环：

- A 创建时需要 B → 去创建 B
- B 创建时需要 A → 又回头要 A
- A 还没创建完 → 死循环

讲义例子：`Husband` 里有 `wife` 属性，`Wife` 里有 `husband` 属性，互相 ref。

---

## 二、前置知识：创建一个 Bean 的两步（理解一切的前提）

| 步骤 | 做什么 | 依赖别人吗 |
|------|--------|-----------|
| ① 实例化 | 调用**无参构造方法**，new 出对象（此时属性全是 null） | ❌ 不需要 |
| ② 属性赋值 | 调用 **setter 方法**，把依赖填进去 | ✅ 需要 |

**核心结论（9.5 节的灵魂）：**

- **set 注入**：① 和 ② 天然是两个独立步骤，中间可以"暂停"——这就是 Spring 能解决它的根本原因。
- **构造注入**：① 和 ② 挤在构造方法里一次完成，构造参数必须在 new 的时候就拿到，**不存在"暂停"的时机**，没有半成品可以提前曝光 → 解决不了。

对应到 Bean 生命周期：**实例化（Instantiation）→ 属性赋值（Populate）→ 初始化（Initialization）**，三级缓存机制就发生在"实例化之后、属性赋值之中"这段窗口期。

---

## 三、四种场景实验结论汇总（9.2 ~ 9.4）

| scope | 注入方式 | 能否解决 | 原因 |
|-------|---------|---------|------|
| singleton | set 注入 | ✅ 能 | 实例化与赋值分离，可提前曝光半成品 |
| singleton | 构造注入 | ❌ 不能 | 两步合一，无半成品可曝光 |
| prototype | set 注入 | ❌ 不能 | prototype 不被缓存，缓存机制整个失效 |
| 一个 singleton + 一个 prototype | set 注入 | ✅ 能 | 环上被第二次获取的是 singleton，能从缓存拿到 |

失败时报的都是同一个异常：`BeanCurrentlyInCreationException`（请求的 bean 正在创建中：是否存在无法解析的循环引用？）。

---

## 四、解决原理：提前曝光（走一遍流程）

```
1. 创建 husbandBean（singleton + set）
   ├─ ① new Husband()              → 半成品（wife = null）
   ├─ 把半成品"曝光"放进缓存          ← 关键动作！
   └─ ② 准备 setter 赋值，发现需要 wifeBean → 转去创建 wifeBean

2. 创建 wifeBean
   ├─ ① new Wife()                 → 半成品（husband = null）
   └─ ② setter 赋值，发现需要 husbandBean
        → 去缓存找 → 拿到第 1 步曝光的半成品 Husband ✅ 无需重新创建
        → wifeBean 赋值完成，成为完整对象

3. 回到第 1 步挂起的地方
   └─ 把完整的 wifeBean 赋给 husband.wife → husbandBean 也完整了
```

**为什么这样就通了？**

单例对象在堆里只有一份。第 2 步塞给 Wife 的是 Husband 对象的**引用（地址）**，哪怕此刻 Husband 还不完整，等第 3 步补完属性后，Wife 手里那个引用指向的就是完整的 Husband —— 后补的赋值对双方都可见。

**一句话：A 不等自己完整就先把半成品暴露出去，B 拿着 A 的引用先完成自己，A 再补完，闭环打通。**

## 五、三级缓存：源码层面的实现

讲义截图里的类是 `DefaultSingletonBeanRegistry`，里面的三个 Map 就是"三级缓存"：

| 级别 | Map 名称 | 存什么 |
|------|----------|--------|
| 一级缓存 | `singletonObjects` | **成品** Bean（实例化 + 赋值都完成） |
| 二级缓存 | `earlySingletonObjects` | **半成品** Bean（new 出来了，属性还没赋） |
| 三级缓存 | `singletonFactories` | `ObjectFactory` 工厂对象（调用它才能拿到早期引用） |

关键方法：

- `addSingletonFactory()`：实例化之后、属性赋值之前，把 Bean 对应的 ObjectFactory **提前曝光**到三级缓存。
- `getSingleton(String)` 查找顺序：**一级 → 二级 → 三级**。三级拿到工厂后调用其 `getObject()` 得到早期对象，升级放入二级缓存，并从三级缓存删除。

上面第四节"去缓存找 Husband"，实际走的路径就是：一级没有（还没做完）→ 三级里有工厂 → 工厂产出半成品引用 → 放入二级。

**记忆口诀：一级放成品，二级放半成品，三级放工厂（能造半成品的作坊）。**

## 六、灵魂拷问：为什么是三级，二级不够吗？（高频难点）

**如果只考虑普通对象，二级确实够了**（一级成品 + 一级半成品）。

第三级存"工厂"而不是直接存对象，是为了配合 **AOP 代理**：

- 一个 Bean 如果被 AOP 切中，容器里最终应该放的是**代理对象**，而不是原始对象。
- 但在"提前曝光"那个时间点，Bean 才刚 new 出来，Spring 还不确定该不该给它生成代理。
- 存一个 `ObjectFactory`（工厂 / lambda），相当于把"给原始对象还是给代理对象"这个决定**推迟到真正被别人需要的那一刻**，并且保证：
  - 不管 B 是走缓存提前拿到，还是等 A 完整后正常拿到，**拿到的是同一个对象**；
  - 不会出现"B 手里是原始对象、容器里是代理对象"这种分裂。

面试时能主动讲出"第三级缓存存在的意义是为了 AOP 代理的一致性"，是明显的加分项。

## 七、面试题清单（Q&A）

### Q1：什么是循环依赖？举例说明

两个或多个 Bean 互相依赖形成闭环。例如 A 中有属性 B（`<property ref="b">`），B 中又有属性 A。A 创建时需要 B，B 创建时又需要 A，若无机制介入会无限递归。

### Q2：Spring 能解决哪些场景的循环依赖？

**只能解决 singleton + setter（属性）注入的循环依赖。**

- 构造器注入的循环依赖：解决不了（实例化和赋值无法分离）。
- prototype 的循环依赖：解决不了（prototype 不缓存，每次 getBean 都新建，没有地方放"曝光的半成品"）。
- 环上只要被第二次获取的那个 Bean 是 singleton，就能从缓存拿到半成品、断开循环（所以 singleton + prototype 混合可以）。

### Q3：说一下三级缓存（标准答题模板）

> Spring 在 `DefaultSingletonBeanRegistry` 中维护三个 Map：一级 `singletonObjects` 存成品 Bean，二级 `earlySingletonObjects` 存提前曝光的半成品 Bean，三级 `singletonFactories` 存能生产早期引用的 ObjectFactory。Bean 实例化之后、属性赋值之前，Spring 会把它的 ObjectFactory 提前曝光到三级缓存；当它依赖的 Bean 反过来需要它时，`getSingleton` 按一级 → 二级 → 三级的顺序查找，从三级缓存的工厂拿到早期引用并升级到二级，从而打破创建闭环。这套机制只在 singleton + setter 注入下生效。

### Q4：为什么构造器注入无法解决循环依赖？

构造注入时，"实例化"和"属性赋值"合并在构造方法调用中一次完成——构造参数里的依赖必须在 new 的那一刻就拿到。对象在构造方法返回前根本不存在，**没有半成品可以提前曝光**，两步无法拆分，循环无法断开，最终抛 `BeanCurrentlyInCreationException`。

### Q5：为什么 prototype 无法解决循环依赖？

三级缓存机制本质是"缓存 + 提前曝光"。Spring 对 prototype Bean **不做缓存**（每次 getBean 都产生新实例），曝光半成品没有地方存；同时每次都是全新创建，无法复用之前的引用，循环永远断不开。

### Q6：Spring 是怎么"发现"循环依赖的？（检测机制）

Spring 用一个 `singletonsCurrentlyInCreation` 的 Set 集合记录正在创建中的 Bean 名字。每个 singleton 开始创建前会执行 `beforeSingletonCreation()` 把名字加进去，**加入前先检查是否已存在**——如果已存在，说明绕了一圈又回到自己，直接抛 `BeanCurrentlyInCreationException`。

### Q7：三级缓存在 Bean 生命周期的哪个阶段起作用？

实例化（调无参构造）之后、属性赋值（populate，调 setter）之前，调用 `addSingletonFactory()` 把 ObjectFactory 放入三级缓存；属性赋值阶段依赖注入时按 一级→二级→三级 查找；全部完成后 Bean 进入一级缓存。

### Q8：@Lazy 能解决构造注入的循环依赖吗？

能（这是构造注入循环依赖的常用出路）。给构造参数（或注入点）加 `@Lazy` 后，Spring 注入的**不是真实对象，而是一个代理**；等第一次真正调用方法时才去容器里 getBean。相当于把"必须立刻拿到对方"推迟到了运行期，创建期的闭环就不存在了。代价：多一层代理、出错推迟到运行期。

### Q9：Spring Boot 2.6 之后循环依赖默认怎么样了？

**默认禁止**，检测到循环依赖直接启动失败，需设置 `spring.main.allow-circular-references=true` 才放开。因为官方认为循环依赖是设计坏味道。正确做法是通过调整代码结构消除循环（抽公共逻辑下沉、事件解耦、`@Lazy` 临时兜底等），而不是依赖框架容忍。

### Q10：循环依赖和 AOP 有什么关系？（进阶）

- 正常 AOP 代理在 Bean **初始化之后**生成。
- 发生循环依赖时，Bean 是在**属性赋值阶段**就被别人拿走了，早于初始化——所以提前曝光的必须是"将来会成为的那个代理对象"，这正是三级缓存存 ObjectFactory 的原因：工厂内部会调用 `getEarlyBeanReference()`，让 AOP（`AbstractAutoProxyCreator`）有机会提前生成代理，保证 B 提前拿到的和容器里最终的是同一个代理对象。
- 反例：`@Async` 的代理不是通过 `getEarlyBeanReference()` 生成的，所以 `@Async` Bean 参与循环依赖时可能提前暴露原始对象，导致异步失效或类型异常——遇到时用 `@Lazy` 解决。这一点知道即可，属于深水区。

## 八、加分项 & 避坑

**加分表达：**

1. 先答结论（只能解决 singleton + setter），再讲机制（两步分离 + 提前曝光 + 三级缓存），最后主动提 AOP 与第三级缓存的关系——层次感立刻出来。
2. 主动说"Spring Boot 2.6+ 已默认禁止循环依赖，实际开发应优先消除环而不是指望框架兜底"——体现工程判断，不背书。
3. 被追问"二级够不够"时：先承认不考虑 AOP 二级就够，再讲工厂延迟决策的一致性意义——这是这道题的胜负手。

**常见坑：**

- ❌ 说"三级缓存能解决所有循环依赖"（构造器、prototype 都不行）。
- ❌ 把三级缓存说成"提高查询性能的缓存"——它是为了**打破创建闭环 + 保证代理一致性**，跟性能无关。
- ❌ 只背三个 Map 名字，说不出"实例化与赋值分离"这个根本前提。

---

## 附：一句话总结

> Spring 把 singleton Bean 的"实例化"和"setter 赋值"拆成两步，在两步之间通过三级缓存把半成品**提前曝光**；依赖闭环中另一方直接从缓存拿这个早期引用，循环被打破。构造注入两步合一、prototype 不进缓存，所以都无解。
